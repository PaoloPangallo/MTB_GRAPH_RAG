3. RAGIONAMENTO SULL'INPUT DELLA PIPELINE
--------------------------------------------------------------------------------
Analisi del benchmark CSV per determinare se l'input fosse realistico.

PROBLEMA IDENTIFICATO: l'input precedente era troppo semplice
  (gene + variante + tumore + linea terapeutica). Non copriva fusioni,
  CNA, biomarker e casi atypical in modo strutturato.

DECISIONI PRESE:

  1. alteration_type è campo di input obbligatorio (non inferibile
     automaticamente dal nome della variante in modo affidabile).

  2. category del benchmark (baseline/resistance/new_target/off_label/
     tumor_agnostic) è usata SOLO nella fase di valutazione per verificare
     il routing atteso — NON è un campo di input della pipeline in produzione.
     Usarla come input = overfitting alla valutazione.

  3. Complexity Check rimane una chiamata LLM (non mapping deterministico
     category→tier) per generalizzabilità in produzione.

  4. "Solid Tumor" è corretto per casi tumor-agnostici (BENCH-016 NTRK1,
     BENCH-023 TMB-High) — l'approvazione FDA è tumor-agnostica, non ha
     senso forzare un tumore specifico.

  5. BENCH-024 EGFR Exon 19 Deletion è alteration_type=atypical, non cna
     — è una delezione in-frame proteica, non una copy number alteration.

STRUTTURA INPUT FORMALIZZATA:

  Campo               Tipo      Valori                          Obbligatorio
  ──────────────────────────────────────────────────────────────────────────
  gene                string    HUGO symbol (null per biomarker)   Sì*
  variant             string    protein change, Fusion, MSI-High   Sì
  tumor_type          string    nome tumore o codice OncoTree      Sì
  alteration_type     enum      point_mutation | fusion | cna |    Sì
                                itd | atypical | biomarker
  therapy_line        string    first-line | second-line |         No
                                later-line
  enrich_with_oncokb  boolean   true | false (default false)       No

  * null per biomarker (MSI-H, TMB-H)

6. IMPLICAZIONI ARCHITETTURALI EMERSE DALLA VERIFICA
--------------------------------------------------------------------------------
Tre implicazioni importanti per l'implementazione del Variant Interpreter:

  1. BRANCHING OBBLIGATORIO per alteration_type
     Il Variant Interpreter non può usare una query unica.
     Due logiche distinte:
       point_mutation → Gene(hugo_symbol)→Variant(variant_name)→MP→Evidence
       tutti gli altri → MolecularProfile.name CONTAINS [termine chiave]
     Nell'implementazione LangGraph: conditional edge post-complexity-check
     che instrada su nodo diverso in base ad alteration_type, OPPURE
     logica if/else dentro un singolo nodo Variant Interpreter.

  2. PRIORITÀ PROFILI SEMPLICI su profili composti
     Nel KB esistono MolecularProfile composti (es. "BCR::ABL1 Fusion AND
     ABL1 T315I", "v::ALK Fusion OR v::ROS1 Fusion"). La query deve
     preferire il match esatto al profilo semplice e restituire i composti
     come evidenze secondarie.
     Implementazione: ORDER BY lunghezza mp.name ASC (profili più corti
     prima) o filtro esplicito.

  3. DIZIONARIO DI MAPPING KB ↔ OncoKB API
     I nomi dei biomarker differiscono tra KB e API:
       KB: "TMB High"  → API: "TMB-H"
       KB: "MSI High"  → API: "MSI-H"
     Serve un dizionario esplicito nel codice per tradurre il nome KB
     nel parametro alteration corretto per la chiamata OncoKB.
